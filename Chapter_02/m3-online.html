Module 2.3 · Platform-specific (Esri)

ArcGIS Online: hosting, sharing and the catalogue

Esri runs the servers; you run an organisation inside it. Everything is an item, items point at each other, and usually only one kind of item holds any data.

In this module you will

  • Name the four things ArcGIS Online is for.
  • Recognise items: web layer, view, web map, group, member, app — and which of them hold data.
  • Keep three things apart: can I see it, can I edit it, may I reuse it.

2.3.1What ArcGIS Online is for

Esri describes ArcGIS Online as “a cloud-based mapping and analysis solution” where data and maps are “stored in a secure and private infrastructure”. Four capabilities matter here:

Hosted mapping

You can “publish data as web layers on ArcGIS Online”, and they are “hosted in the Esri cloud and scale dynamically”. That is R2 storage + R3 services for hosted layers — Esri operates the machines; you never see them.

Sharing

Content can be shared “with anyone, anywhere or keep them private”; you can create groups, private or public.

Content management

Web maps, scenes, apps and notebooks are created and stored as items with metadata and an owner — R4 content organisation.

Organisation administration

Administrators “configure security, manage members” and set terms of use.

Two facts developers ask about immediately

Who runs it? Esri. You do not install, patch, back up or scale ArcGIS Online. You administer an organisation inside it. (This is the key contrast with ArcGIS Enterprise, next module.)

Credits. Esri says “credits are the currency used across ArcGIS and are consumed for specific transactions and types of storage, such as storing features, performing analytics, and using premium content” — and that “most of what you do in ArcGIS Online does not require credits”. Nothing in this chapter uses any. Never guess credit costs from memory; look up the current table.

Developer view

ArcGIS Online is closest to a managed cloud platform: storage, an API layer, identity and a catalogue with no servers to run. Where the comparison stops: unlike a bucket of files, items reference one another (a map references layers; an app references a map), and sharing works on each item separately.

2.3.2Items, and which of them hold data

Everything in ArcGIS Online is an item. Below is the item diagram for our practice deployment, Solution S-2. Click any box to see what it stores, what it points at, and what would happen if it were deleted. Then try the delete buttons.

Try it
Click a box, or press a delete button and watch what breaks.

The arrows are the whole point. Only the filled boxes hold data. The view reads the same data with different settings — Esri: a view “is a view of the data in the source layers, which means edits made to the data in the source appear in the view”. Web maps hold styling and pop-ups and point at layers — Esri: a web map references layers rather than storing data. Apps hold their own settings and point at maps. In a healthy deployment most items hold no data at all.

Two consequences

Deleting is one-sided. Esri: “If you delete a hosted layer, the data stored in ArcGIS Online is deleted.” Deleting a web map removes only its configuration; the layer and data remain — but deleting the layer breaks every map and app that pointed at it.

Styling can live in more than one place. Two web maps can point at the same layer and draw it differently — just as two ArcGIS Pro maps can (2.2.3). Asked “where is the red symbol defined?”, the answer is usually a map — and if the evidence does not say which map, the right answer is “not enough information” (module 2.7).

Worked example: the public should see locations but not notes

The office wants citizens to see request locations but not the reporter’s phone channel or free-text notes, while the inspection team sees and edits everything. Publishing a second copy for the public would create two datasets that drift apart — the authoritative-copy problem from 2.1.3. Esri’s documented pattern instead: create a hosted feature layer view, exclude the sensitive fields from the view, keep it read-only, share the view publicly and keep the source layer for the group. Esri’s own wording: let organisation members edit the layer “but share a read-only feature layer view with the public”, and exclude fields “if the view users do not need to access them”. One authoritative dataset; two items with different sharing and field visibility. Check it by editing a note on the source and confirming the public view shows the location with no note field.

2.3.3Visible ≠ editable ≠ reusable

Three separate things are easy to muddle. Toggle each one and read the verdict.

Try it

1 · Can I see it?

Set per item by its sharing level: owner only · organisation · groups · everyone. A map you can open without signing in is shared with everyone.

2 · Can I edit it?

A separate setting on the layer. Off by default. Public editing needs an extra explicit approval step. Esri recommends a read-only view for the public and the editable layer for a group.

3 · May I reuse it?

A licence / terms-of-use question, not a technical one. Seeing or downloading says nothing about republishing or combining it. Chapter 7 puts this on the intake form.

Developer view

A public GitHub repository is readable by anyone, writable only by collaborators, and reusable only under its licence — three independent facts. Exactly the same here. Where it stops: ArcGIS edit permission can be limited to attributes only, and a view can expose a subset of fields; Git has no clean equivalent.

Misconception

“It’s on a public map, so it’s open data.” A developer scrapes a public layer into their own service and republishes it, breaking the owner’s terms — or treats an out-of-date public copy as authoritative for a decision.

Deferred: configuring sharing levels, groups and editing settings step by step, and managing roles, are later administration topics. For now you only need to read them off an item card.
