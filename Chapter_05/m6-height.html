Module 5.6 · General GIS idea

Height needs a reference too: height = 30 means nothing yet

Horizontal position was two numbers plus a CRS. Height is one number plus a vertical reference — and the same ambiguity applies. This module shows the three surfaces a height can be measured from, why “height above ground” and “elevation” are different things, and why having a Z value is not the same as using it.

In this module you will

  • Name what a vertical coordinate system defines: surface, unit, direction.
  • Tell ellipsoidal height from height above sea level, and both from height above ground.
  • Explain why a stored Z does not guarantee that a later operation uses it.

5.6.1Three surfaces, three heights

Esri’s definition: a vertical coordinate system “defines the origin for height or depth values”, “includes a unit of measure. This is always a linear unit, usually feet or meters”, and “includes a direction. This specifies whether values are positive up, representing heights above a surface, or positive down, indicating that values are depths below a surface”. The surface it measures from — the vertical datum — comes in two kinds. Look at the three arrows on the picture.

Ellipsoidal height (h)

Measured from the smooth ellipsoid of 5.3. This is what a GPS receiver natively produces, and it is what GeoJSON’s optional third number means: “height in meters above or below the WGS 84 reference ellipsoid”. EPSG example: EPSG:4979, “WGS 84” Geographic 3D — axes “latitude, longitude, ellipsoidal height”, units “degree, degree, metre”.

Height above sea level (H)

Measured from a surface that follows gravity and approximates mean sea level — the geoid. This is what “elevation” on a survey plan or a topographic map means. EPSG example: EPSG:3855, “EGM2008 height” — datum “EGM2008 geoid”, axis “height (H). Orientation: up. UoM: m”, described as a “Zero-height surface approximating mean sea level”.

The one thing to carry forward

The geoid and the ellipsoid are different surfaces, so h and H are different numbers for the same point. How different depends on where you are — you need a geoid model to find out, and that is beyond this chapter. What you must remember: a height is meaningless until you know which surface it is measured from, in what unit, and in which direction.

Worked example: the streetlight record SL-0113, height = 30

The asset register stores just the number 30. Try to give it a meaning by choosing answers, and watch how the meaning swings.

Try it

The record is undefined as stored. It cannot be repaired by staring at the number. It needs a unit, a reference (in the data or in the metadata), and a schema rule saying what “height” means for a streetlight — that rule is written in Chapter 8. This chapter’s job is to refuse to interpret 30 without it.

5.6.2Height above ground is not elevation

Height above ground (relative)

How far a thing is above the local ground. A pole is 9 m tall whether the street is at sea level or up on a plateau.

Elevation (absolute)

The height of a point above a vertical datum. The base of the same pole might be at 55 m above the EGM2008 geoid.

Try it

They add up, but they do not substitute for each other — and a column called height could hold either. Chapter 4 made the same distinction for rasters (terrain versus a surface that includes buildings and trees). The same demand applies to every Z value in a feature dataset: the dataset’s own definition must say which.

Developer view

./logs is relative to where you are; /var/app/logs is absolute. Both are “a path”. A height above ground is a relative path; an elevation is an absolute one; a value with no indication of which is a bug waiting to happen. Where the analogy stops: an operating system resolves a relative path from the working directory. There is no “working directory” for a height — the reference has to be written down explicitly.

5.6.3A stored Z does not mean an operation uses Z

A dataset can carry Z values and still be treated as flat by the next tool. Three checked examples:

WhereWhat the documentation saysLesson
ArcGIS Maps SDK for JavaScript PointThe hasZ property “Indicates if the geometry has z-values (elevation)”; when false, z-values are excluded from the geometryA z number being present is not the same as the geometry being three-dimensional
GeoJSON (RFC 7946)A third element is allowed but not required; “In the absence of elevation values, applications sensitive to height or depth SHOULD interpret positions as being at local ground or sea level”Many applications are not height-sensitive at all
ArcGIS Pro XY Table To PointZ is a separate optional field; only when a Z Field is given does the output carry a vertical coordinate systemZ is opt-in, tool by tool
Course rule

Each operation’s dimensional behaviour is verified when that operation is introduced. Chapter 6 states whether each measurement it uses is 2D or 3D. Nothing in this chapter entitles you to assume that a distance “includes the slope” because the data has Z.

Misconception

“The survey has Z, so our distances are true 3D ground distances.” They are whatever the tool computes — usually flat 2D unless the documentation says otherwise.
