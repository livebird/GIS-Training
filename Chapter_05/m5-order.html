Module 5.5 · Format rules and API contracts

Coordinate order: “lat, long” is not a file format

People say “lat, long”. GeoJSON writes longitude first. Leaflet takes latitude first. The same two numbers, in the same order, mean different places under different contracts. This module gives you the rule, the verified contracts, and the swap that slips past every range check.

In this module you will

  • State the rule: coordinate order follows the actual interface contract.
  • Write a GeoJSON point correctly and say what its CRS is (you do not get to choose).
  • Detect a swapped pair that a range check cannot catch.

5.5.1The rule, and the contracts that were checked

The one rule

Coordinate order follows the actual interface contract — the specification of the file format, the API, the library class or the database function you are using. Not the CRS record, not the prose, not your memory of the last project.

Why is there confusion at all? The formal EPSG record for 4326 lists its axes as “latitude, longitude”. Yet most GIS engines store geographic data as x = longitude, y = latitude, because x is the left–right axis of a screen. Neither side is wrong: one is a conceptual axis order, the other a storage convention. Each row below is a different contract, read from official documentation on 19 September 2026. None implies the others.

Look at rows 1 and 5: the same developer can write GeoJSON ([lng, lat]) in the morning and a Leaflet marker ((lat, lng)) in the afternoon. That is normal. What is not acceptable is not knowing which contract is in force.

5.5.2GeoJSON (RFC 7946): longitude, then latitude, on WGS 84 — no choice

GeoJSON is the format developers meet first, so here are its rules exactly, from the standard:

  1. Order. “A position is an array of numbers. There MUST be two or more elements. The first two elements are longitude and latitude, or easting and northing, precisely in that order and using decimal numbers. Altitude or elevation MAY be included as an optional third element.” (§3.1.1)
  2. CRS is fixed. “The coordinate reference system for all GeoJSON coordinates is a geographic coordinate reference system, using the World Geodetic System 1984 (WGS 84) datum, with longitude and latitude units of decimal degrees.” (§4) The standard says this is equivalent to the OGC identifier urn:ogc:def:crs:OGC::CRS84, and that the old crs member “has been removed from this version of the specification because the use of different coordinate reference systems … has proven to have interoperability issues”.
  3. Third element. “An OPTIONAL third-position element SHALL be the height in meters above or below the WGS 84 reference ellipsoid.” (§4) — module 5.6 explains why “above the ellipsoid” matters.
  4. Precision. Six decimals is “about 10 centimeters”; implementations “should consider the cost of using a greater precision than necessary”. (§11.2)
Worked example

Write point G1 (latitude 23.0250, longitude 72.6000, EPSG:4326) as a GeoJSON Point. Rule 1 puts longitude first; rule 2 means no CRS member is written; G1 is already in WGS 84 degrees, so nothing needs converting.

{ "type": "Point", "coordinates": [72.6000, 23.0250] }
                                   ↑ longitude   ↑ latitude

What this does not establish: if the source had been in EPSG:32643 metres, writing the numbers into GeoJSON would be wrong even with the order right — rule 2 fixes the CRS, so the values would first have to be converted (Chapter 6).

The name clash to remember

GeoJSON’s CRS is CRS84: longitude, latitude on WGS 84. The formal EPSG:4326 record is latitude, longitude on WGS 84. Same datum, same units, opposite axis order. Many tools label GeoJSON output “EPSG:4326” because datum and units match — usually harmless, unless a consumer honours the formal EPSG axis order and swaps the values. If a library has a setting about “axis order” or “authority axis order”, this is the problem it exists for. Check its documentation; do not assume.

Developer view

A tuple [a, b] in an API has meaning only because the schema says index 0 is a. GeoJSON’s schema says index 0 is longitude. Where the analogy stops: a schema validator would reject a wrongly typed value; a GeoJSON validator cannot reject [23.025, 72.6], because both numbers are legal decimals inside the allowed ranges. The error is in the meaning, not the syntax — which is the whole point of the next section.

5.5.3The swap that passes every range check

A script exports G1 from a CSV whose columns are lat, lon. The developer builds the array in column order — a natural mistake — and writes "coordinates": [23.0250, 72.6000]. By the RFC, index 0 is longitude, so this point is at longitude 23.025°E, latitude 72.6°N: in the sea off northern Norway. And a range check accepts it: 72.6 is a legal latitude, 23.025 a legal longitude. Test it below with your own numbers and an expected area.

When a range check does help. A pair like [151.21, −33.87] swapped to [−33.87, 151.21] fails the latitude range (151.21 > 90) and is caught. Only pairs where both absolute values are ≤ 90 slip through — which includes all of India, most of Europe and most of the Americas. Do not rely on luck.

Misconception

“I use a library, so ordering is handled.” The library applies its contract to your input. Feed it (lat, lon) where it expects (x, y) and it will happily put your points in the sea. Libraries convert between CRSs on request; none of them can know which of your two columns is which.
